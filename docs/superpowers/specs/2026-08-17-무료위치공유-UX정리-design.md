> "100% 자동화가 목표가 아니야. 글 쓰는 걸 자동화하는 게 목표지. 장소는 묶어서 스토리 짜기 위해서,
> 그리고 방문객한테 정확한 위치를 공유해주기 위해서 하는 거야. 처음에 분류하고 유저가 수정해

이 한 문장이 설계를 바꿨다 — 정답은 '위키 정보 카드'가 아니라 **정확한 위치 링크 + 사용자가 고칠 수 있는 입력**이었다.

## A. 무료(유료 키 없이) 위치 공유

### 실측 — 무료로는 리치 OG 카드가 불가능하다

후보 URL들의 og 태그를 직접 크롤한 결과:

| 후보 | og:title | 결과 |
|---|---|---|
| `google.com/maps/search/?api=1&query=…` (키 없음) | 없음 | "Google 지도" 일반 카드 |
| `map.naver.com/p/search/…` | 없음(SPA) | 카드 불가 |
| `openstreetmap.org/?mlat=…` | "OpenStreetMap" | 일반 카드 |
| 유료 `place_id` URL | 장소명 | 리치 카드 (기존 경로) |
| `ko.wikipedia.org/wiki/…` | 문서명 + og:image | **리치 카드 가능** |

### 기각안

- **무료 URL로 OG 카드 유도** — 장소명이 없는 일반 카드는 글을 지저분하게 만든다.
- **OSM 타일 Selenium 캡처** — 타일 사용정책이 "헤드리스 봇의 팬/줌 강제 렌더링"을 금지로 명시.
  구글맵 캡처도 Maps Platform 약관상 재배포 제한(Codex 자문도 같은 결론).
- **좌표 → 위키 문서 자동 해석(GeoSearch)** — 반경 검색이 엉뚱한 문서를 잡는다
  (고베 좌표 → "고베시"). 신뢰 기반 원칙 위반이라 기각, 이름 기반 교차검증만 채택.

### 채택 설계

1. **위치 링크(주 수단)** — 사진 좌표 → `maps/search/?api=1&query=<lat>,<lon>` (키 불필요)을
   `<!--MAPLINK:url|text-->` 마커 → `map_link` 블록 → `_paste_hyperlink`로 삽입.
   **OG 카드가 아니라 하이퍼링크**라 레이아웃을 해치지 않고, 본문 텍스트 URL 미노출 불변식도 유지된다.
2. **사용자 지정 우선** — 계획검수 stop에 `map_url` 필드. 비우면 좌표 자동, 붙여넣으면 그 링크.
   자동 분류 후 사람이 고친다는 방침 그대로.
3. **위키 장소 카드(보조)** — 유료 `place_id`가 없을 때만. 이름 정확일치 + 좌표 30km 교차검증 +
   동음이의 제외일 때만 채택하고 아니면 조용히 생략.
   **실측 발동률: 사용자 확정 장소명 20개 중 0건**(랜드마크 정확명은 5/6 채택).
   보수적이라 해롭지 않지만 기대할 기능은 아니다.
4. `blocks_to_html`이 `map_link`/`map_card`를 실제 `<a>`로 렌더 — 이전엔 URL을 버려
   로컬 저장본에서 위치가 사라졌다.

우선순위: 유료 키가 있으면 기존 구글맵 place 카드가 그대로 우선한다.

## B. 사용자 입력 정리 (23개 → 기본 8 + 고급 8)

원칙: **결과에 실제 영향을 주는 축만 1차 화면에 남기고, 죽은·중복 입력은 제거**(Codex 자문 반영).

- **삭제**: 네이버 ID/PW(발행기는 `os.environ`만 읽어 **미사용인데 평문 저장**이었다),
  발행 방식(클립보드 경로 폐기), Google Maps 키(.env 전용), 설정 화면의 중복 URL칸.
- **통합**: 사진설명/장소소개 길이 → 분량(짧게·보통·자세히, `DENSITY_PRESETS`가 전개),
  말투·톤 → 문체 소스(직접 설정 / 참고 블로그). 참고 선택 시 말투·톤은 숨긴다(코드가 양보시키므로).
- **고급 접기**: 이모지·꿀팁·마무리·색상·구분선·라벨·인트로·모델.
- **호환**: `migrate_settings()`가 옛 파일을 자동 변환(멱등), `save_settings()`는 런타임·폐기 키를
  파일에 쓰지 않는다.

## C. 단계 플로우 6 → 4

측정으로 드러난 문제: 계획검수가 6초간 "불러오는 중"(`/api/photos` 7.97초), 미리보기 패널이
준비·검수·생성에서 안내문만 띄우며 화면 절반 점유, 삭제한 설정의 잔재가 발행 화면에 생존,
사장 코드 5개 함수(참조 DOM 0개).

```
1. 준비(설정 접힘 + 업로드) → 2. 계획 검수 → 3. 원고(생성→편집) → 4. 발행
```

- 설정은 최초 1회만 필요, 생성→편집은 끊김 없는 한 흐름이라 합쳤다.
- 단계 숫자를 `PREP/PLAN/DRAFT/PUB_STEP` 상수로(호출부 12곳). 내부 함수명도 역할 이름으로.
- 원고 단계는 저장된 초안이 있으면 편집 화면을 연다 — `has_drafts`(메모리) **OR**
  `has_saved_drafts`(디스크). 재시작 후엔 디스크가 진실원.
- 미리보기 패널은 결과물이 있는 단계(원고·발행)에서만. 준비·검수는 본문 전폭.
- 썸네일 캐시로 `/api/photos` **7.97초 → 0.26초**, 프론트는 계획을 먼저 그리고 썸네일을 나중에 채운다.
