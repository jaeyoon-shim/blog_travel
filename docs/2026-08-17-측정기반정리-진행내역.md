## 1. 발행 진행표시 (`a9c5948`)

**문제**: 발행 task가 상태를 "발행 준비 중"으로 1회만 세팅하고 이미지 삽입 루프(34장 ≈ 12분)
동안 갱신하지 않아 멈춘 것처럼 보였다(2026-07-06 관찰의 후속 과제).

**수정**
- `posters.publish_progress(done, total, lo=10, hi=90)` — 순수함수로 분리해 단독 테스트.
- `NaverSeleniumPoster.post(progress_cb=)` — 준비/에디터/제목/**블록별+사진 카운터**/발행창/
  공개설정/태그/최종확인 단계 보고. 콜백 예외는 전부 흡수(발행을 죽이면 안 됨).
- `NaverPoster` 파사드 전달 → `/api/publish`·`/api/publish_all`이 `state["progress"]`에 반영.
  전체 발행은 글 내부 진행률을 `[i, i+1]/total` 구간에 매핑.
- 프론트는 이미 `/api/status`를 800ms 폴링하므로 UI 변경 없음.

**검증**: 유닛 3건 + 라우트 E2E(발행기 스텁, 네이버 미접촉) — 상태 스냅샷 **2개 → 14개**,
퍼센트 단조증가, `사진 12/12` 노출. 전체발행은 1번글 ≤33% · 3번글 ≥66% 구간 매핑 확인.

## 2. 계획검수 장소 과분할 (`b2af99b`, `85b9f9b`)

**2-1. 원래 백로그가 실데이터에서 반증됨**
핸드오프 최우선 항목이던 "`place_groups`가 비연속 재방문을 병합"을 착수 전 측정:
`plan.json`의 stop 시간구간 **교차 0건**, 그리고 섹션 구조를 정하는 층은 GPS `location_name`이
아니라 **plan stop**이었다(`groups_from_plan`이 stop 이름으로 덮어씀).
그대로 "연속 run 그룹핑"을 구현했다면 3일차 섹션이 6개 → **49개로 폭발**.

**2-2. 진짜 결함 = 자동 stop 과분할**

| 일차 | 사진 | 자동(구) | 사용자가 손으로 정리 |
|---|---|---|---|
| 3일차 | 62장 | 31개 | 6개 |
| 2일차 | 34장 | 20개 | 8개 |
| 1일차 | 6장 | 5개 | 3개 |

원인은 `_stops_for_day`의 '확신 이름 키 + ~110m 격자'. 무료 모드 역지오코딩 세부명이 같은 장소
안에서 관광지/공원/거리/신사/주차장으로 갈리고 격자 경계까지 겹쳤다.

**수정**: **시간·거리 세션 클러스터링**(45분·300m). 순수함수 `_exif_seconds`, `_stop_name` 분리,
호출부가 정렬을 보장하지 않으므로 내부에서 시간순 정렬.

임계값은 **사용자가 확정한 plan stop을 정답 레이블**로 두고 사진쌍 P/R/F1 그리드서치로 결정:

| 방식 | 평균 F1 |
|---|---|
| 이름키 + 110m 격자(구) | 0.456 |
| **세션 45분/300m (채택)** | **0.940** |
| 세션 30분/300m | 0.908 |
| 세션 45분/200m · 500m | 0.815 · 0.797 |
| v2(세션 + 확신이름 경계) | 0.841 ← 직관적이지만 패배 |

**2-3. 재방문 계약 변경**: 사이에 다른 장소가 낀 동명 stop = 재방문 → `이름 (재방문)`으로 구분
(하류가 전부 name 키로 묶어 메모·별점·지시가 서로 덮어쓰던 문제).
**연속된 동명 stop은 재방문 아님**(헛 섹션 방지 — 실데이터 재초안에서 발견).
`merge_user_edits`는 사용자가 손댄 구 stop을 재초안이 쪼개면 되붙인다(사용자 확정이 진실원).
옛 계약을 못 박던 테스트 2건은 새 계약으로 갱신.

**검증**: 유닛 99 passed / 실 라우트 E2E `/api/plan/draft` 자동 stop **45개 → 21개**(확정 20개),
디스크 미기록 / **실 OpenAI 생성** — 재방문 1일차에서 `연화의湯` / `연화의湯 (재방문)` 분리,
사진 12/12 순서 일치 / 실데이터 재초안에서 사용자 편집 전량 보존.

## 3. 0원 위치 공유 + 입력 정리 (`0b70757`)

**3-1. 무료로는 리치 OG 카드가 불가능**(og 태그 직접 크롤):

| 후보 | 결과 |
|---|---|
| 키 없는 구글맵 URL | og:title 없음 → "Google 지도" 일반 카드 |
| 네이버 지도 URL | OG 없음(SPA) |
| OSM | 일반 카드 / 타일 정책이 헤드리스 봇 렌더링 금지 |
| 한국어 위키백과 | og:title+og:image → 리치 카드 가능 |

**3-2. 채택 설계** — 사용자 목적 정정("정확한 위치 공유 + 사람이 고칠 수 있게")에 맞춤:
- **좌표 하이퍼링크**(주): `<!--MAPLINK:url|text-->` → `map_link` 블록 → `_paste_hyperlink`.
  OG 카드가 아니라 링크라 레이아웃 무해 + 본문 URL 미노출 불변식 유지.
- **사용자 지정 우선**: 계획검수 stop에 `map_url` 필드(비우면 좌표 자동).
- **위키 카드**(보조): 이름 정확일치 + 좌표 30km 교차검증일 때만. **실측 발동률 0/20**
  (랜드마크 정확명은 5/6) — 보수적이라 무해하나 기대할 기능은 아님.
- `blocks_to_html`이 `map_link`/`map_card`를 실제 `<a>`로 렌더(이전엔 URL을 버려 저장본에서 위치 소실).

**3-3. 입력 정리 23개 → 기본 8 + 고급 8**
- 삭제: 네이버 ID/PW(**미사용인데 평문 저장**이었다), 발행방식(클립보드 폐기), Google 키(.env 전용),
  설정 화면 중복 URL칸.
- 통합: 사진설명/장소소개 길이 → 분량(`DENSITY_PRESETS`), 말투·톤 → 문체 소스(직접/참고).
- 고급 접기: 이모지·꿀팁·마무리·색상·구분선·라벨·인트로·모델.
- `migrate_settings()` 멱등 변환, `save_settings()`는 런타임·폐기 키를 파일에 쓰지 않음.

**검증**: 유닛 108 passed / 실 settings.json 마이그레이션(3~4줄→"자세히", 참고URL 3개→reference,
평문 비번 제거) / 실데이터 체인 — UI 입력 → 자동저장 → `plan.json` → groups → 생성 HTML
(사용자지정 1·좌표자동 7) → 발행 블록 8개 → 저장 HTML `<a>` 유지, 본문 URL 노출 0.

## 4. 6단계 → 4단계 플로우 (`8971b44`)

**측정으로 드러난 문제**: 계획검수 6초 "불러오는 중"(`/api/photos` **7.97초**), 미리보기 패널이
준비·검수·생성에서 안내문만 띄우며 화면 절반 점유, 삭제한 "발행 방식"이 발행 화면에 생존,
사장 코드 5개 함수(참조 DOM `#peList/#grpList/#modeSel` 0개).

```
1. 준비(설정 접힘 + 업로드) → 2. 계획 검수 → 3. 원고(생성→편집) → 4. 발행
```

| STEP | 화면 | render 함수 | 비고 |
|---|---|---|---|
| 1 | 📸 준비 | `renderPrepare` | `settingsHtml()`(details로 접힘) + `uploadHtml()` + [다음: 계획 검수 →] |
| 2 | 🗂 계획 검수 | `renderPlanStep` | 본문 전폭 |
| 3 | 🤖/✏️ 원고 | `renderDraftStep` → `renderGenerate`/`renderEditor` | 저장 초안 있으면 편집으로 자동 분기, 양방향 전환 버튼 |
| 4 | 🚀 발행 | `renderPublishStep` | 미리보기 유지 |

- 단계 숫자 → `PREP/PLAN/DRAFT/PUB_STEP` 상수(호출부 12곳). 내부 함수명도 역할 이름으로
  (`renderS1`이 STEP2를 그리던 어긋남 해소).
- 원고 단계 분기는 `has_drafts`(메모리) **OR** `has_saved_drafts`(디스크) — 재시작 후엔 디스크가 진실원.
- `/api/photos` 썸네일 캐시(`(경로, mtime, 크기)` 키) → **7.97초 → 0.26초(31배)**.
  프론트는 계획을 먼저 그리고 썸네일 도착 시 카드만 다시 그린다.
- 미리보기 패널은 원고·발행에서만(`setPreviewPanel`), 준비·검수는 `.app.no-preview` 전폭.
- 진행 표시(.done)를 4단계 기준 재매핑(발행 완료까지 반영).

**검증**: `/browse`로 4단계 전 화면 렌더 — 콘솔 에러 0, 서버 에러 0, 계획검수 즉시 표시,
패널 토글(준비·검수 `none` / 원고·발행 `flex`), 저장 초안 자동 로드, 진행 표시 정상.

## 트러블슈팅 기록 (lessons-learned 22건 추가)
- 코드 독해로 만든 백로그는 착수 전 **실데이터로 재확인** — 안 그러면 개선이 아니라 사고
- 사용자 확정본 = 공짜 정답 레이블(F1로 파라미터를 계산으로 결정)
- 한 층을 고치면 다음 층 계약이 드러난다(클러스터링 → 동명 재병합 → 재초안 헛 재방문, 3단 연쇄)
- 화면이 느리면 렌더 코드 전에 **API 응답시간부터** 측정(`curl -w %{time_total}`)
- "초안 있음"의 진실원이 둘(메모리/디스크) — 재시작 후에도 참인지 확인
- base64 blob 안의 우연한 `http`가 URL 검사 오탐 → `https?://` 스킴 패턴으로
- `time` 모듈 속성 패치는 프로세스 전역(E2E에서 내 지연까지 사라짐)
- 외부 LLM 자문: Codex만 응답, Gemini는 MCP·CLI 둘 다 실패 → **없으면 없다고 보고**
