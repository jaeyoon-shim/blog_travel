## 무엇을 했나 (2026-08-17)

6주 공백 후 재개. 핸드오프의 남은 후보 중 **측정으로 우선순위를 다시 정하고** 두 건을 근본수정했다.

1. **발행 진행표시 배선** (`a9c5948`)
   - 발행 task가 "발행 준비 중"을 1회만 세팅해 사진 삽입 루프(34장 ≈ 12분) 동안 멈춘 듯 보이던 문제.
   - `posters.publish_progress()` 순수함수 + `NaverSeleniumPoster.post(progress_cb=)` 단계별 보고(준비/에디터/제목/**블록별+사진 카운터**/발행창/공개설정/태그/최종확인) → `NaverPoster` 파사드 → `/api/publish`·`/api/publish_all`이 `state["progress"]`에 반영. 전체 발행은 글 내부 진행률을 `[i, i+1]/total` 구간에 매핑.
   - 프론트는 이미 `/api/status`를 800ms 폴링하므로 UI 변경 없음.

2. **계획검수 장소 과분할 근본수정** (`b2af99b`, 후속 `85b9f9b`)
   - `TripPlanner._stops_for_day`를 '확신 이름 키 + ~110m 격자' → **시간·거리 세션 클러스터링(45분·300m)** 으로 교체. 무료 모드 역지오코딩 세부명(관광지/공원/거리/신사/주차장)이 같은 장소 안에서 갈리며 stop이 심하게 쪼개지던 문제.
   - `groups_from_plan`: 사이에 다른 장소가 낀 동명 stop = **재방문**으로 구분(`이름 (재방문)`). 이전엔 하류가 전부 name 키로 묶어 두 방문이 한 섹션으로 재병합되고 메모·별점·지시가 서로를 덮어썼다. **연속된 동명 stop은 재방문이 아니다**(헛 섹션 방지).
   - `merge_user_edits`: 사용자가 손댄 구 stop을 재초안이 다시 쪼개면 되붙인다(사용자 확정이 진실원).

## 열린 결정 / 주의

- **`place_groups` 비연속 재방문 병합은 실데이터에서 문제가 아니었다** — 핸드오프에 최우선으로 적혀 있었으나 stop 시간구간 교차 0건이었고, 섹션 구조를 정하는 층은 GPS `location_name`이 아니라 **plan stop**이다. 그대로 구현했으면 3일차 섹션이 6개→49개로 폭발했다. 코드 독해로 만든 백로그는 착수 전 실데이터로 재확인할 것.
- 재방문 표시가 `연화의湯 (재방문) (延羽の湯)`처럼 괄호가 겹쳐 보일 수 있다(AI가 현지명을 덧붙임). 검수 화면에서 stop 이름을 다르게 바꾸면 접미는 붙지 않는다.
- 발행 Chrome은 절대 taskkill 금지(네이버 세션 무효화) — 코드가 `poster.close()`로 정리한다. 서버 재시작 후 5000 리스너가 1개인지 확인(`app.py`가 이중 기동은 차단함).
